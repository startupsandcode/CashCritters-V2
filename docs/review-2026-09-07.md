# Cash Critters review, September 7, 2026

## Implemented

- Dashboard now derives lesson completion, the next available lesson, completed-track badges, savings totals, and the savings-goal badge from persisted user data.
- Locked tracks can no longer be entered through a direct lesson URL. Lesson completion authenticates, validates lesson identity and prerequisites, and scores submitted answers on the server. Failed saves preserve answers and offer a retry message.
- Savings validation rejects fractions of a cent, including values that would round to zero in Postgres. Mutations invalidate savings and dashboard pages.
- Leaderboards require authentication, validate game/limit arguments, and no longer fetch or use email addresses as display-name fallbacks. Display names use the first name token.
- Protected layout requires a user ID, not merely a truthy session object.
- Added accessible titles/descriptions to mobile navigation dialogs.
- Updated Next.js to 15.5.24 and migrated the two dynamic lesson routes to asynchronous params. Updated compatible dependencies, including Auth.js beta.32 and Auth core 0.41.3. Removed unused Faker and bundled Vercel CLI dependencies.
- Added a portable test runner, explicit typecheck command, direct ESLint command, and corrected setup instructions so Prisma and Next.js share `.env`.

## Remaining findings

1. **Dependency follow-up:** npm audit reports 5 remaining transitive findings (4 high, 1 moderate), with no critical findings. These concern deepmerge-ts through Prisma configuration and PostCSS bundled by Next.js. Compatible automatic fixes were applied; further major upgrades/overrides need separate compatibility checks. Audit counts describe dependency advisories, not proven exploitability of every application route.
2. **Account readiness:** registration has no parent-account/child-profile mechanism, despite the privacy page describing parent-managed accounts. The privacy contact uses `privacy@cashcritters.example`. Resolve the intended account flow and real contact details before public launch.
3. **Authentication robustness:** credentials registration needs request throttling, stronger runtime validation, duplicate-registration race handling, and a password recovery flow. Server actions must validate runtime input even when TypeScript signatures are strict.
4. **Competitive score integrity:** games submit client-calculated scores. Bounds validation rejects impossible ranges but cannot establish that a game was played. Server-issued runs and replay validation would be needed for a trustworthy competitive leaderboard. Save failures in game clients currently log to the console rather than offering a retry UI.
5. **Leaderboard growth:** the leaderboard loads every score and deduplicates in memory. Aggregate personal bests in the database before large-scale use.
6. **Public-page polish:** About and Terms footer links are placeholders, and the homepage's “thousands of families” claim needs substantiation or revised copy.
